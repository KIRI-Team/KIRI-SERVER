# Flyway 마이그레이션 작성

`ddl-auto: validate`라서 Hibernate는 스키마를 만들지 않고 검사만 합니다. 엔티티와 마이그레이션이 다르면 앱이 기동하지 않습니다.

## 1. 버전 번호 정하기

```bash
git fetch origin
git ls-tree --name-only origin/develop src/main/resources/db/migration/
ls src/main/resources/db/migration/
```

- develop과 현재 브랜치 중 가장 큰 번호 + 1을 사용
- 파일명: `V{번호}__{snake_case 설명}.sql` (언더스코어 2개). 예: `V5__create_question_tables.sql`
- 이미 커밋된 `V*.sql`은 절대 수정하지 않음 (CI가 막음). 고칠 게 있으면 다음 번호로 새 파일

## 2. DDL 작성 (PostgreSQL)

기존 `V1`, `V2` 파일과 같은 스타일로 작성합니다.

| Java | PostgreSQL |
|---|---|
| `Long id` (IDENTITY) | `BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY` |
| `Long` FK | `BIGINT` + `CONSTRAINT fk_{테이블}_{참조테이블} FOREIGN KEY (...) REFERENCES ...` |
| `String` + `length = n` | `VARCHAR(n)` (length 없으면 `VARCHAR(255)`) |
| 긴 본문 | `TEXT` |
| `Integer` / `Boolean` | `INTEGER` / `BOOLEAN` |
| `LocalDateTime` / `LocalDate` | `TIMESTAMP` / `DATE` |
| enum (`EnumType.STRING`) | `VARCHAR(20)` |
| `BaseEntity` | `created_at TIMESTAMP NOT NULL DEFAULT now()`, `updated_at TIMESTAMP` |

- 테이블·컬럼명은 엔티티의 `@Table`, `@Column(name)`과 정확히 같게
- `nullable = false`면 `NOT NULL`, 엔티티의 `@UniqueConstraint(name)`과 같은 이름으로 `CONSTRAINT uk_...`
- 테이블 위에 `-- 한글 설명` 한 줄
- 글자 수 제한은 기획 값 그대로 `VARCHAR(n)`으로 쓰고 요청 DTO `@Size(max = n)`과 맞춤. n은 바이트가 아니라 글자 수라 512 같은 2의 거듭제곱으로 맞출 이유 없음
  - 기획이 정해지지 않았으면 TEXT보다 임시 제한으로 시작 (`VARCHAR` 늘리기는 즉시 끝나지만, TEXT에 제한을 걸려면 초과 데이터부터 정리해야 함)
  - `columnDefinition = "TEXT"`면 `length`는 무시됨. 둘을 같이 쓰지 않음
- PostgreSQL UNIQUE는 NULL끼리 중복으로 보지 않음. nullable 컬럼(예: `fixed_day`)에 걸어도 null 행은 여러 개 가능
- 두 테이블이 서로를 `NOT NULL` FK로 참조하면 어느 쪽도 먼저 INSERT할 수 없음 (예: `family.owner_id` ↔ `member.family_id`). 한쪽은 nullable로

```sql
-- 질문
CREATE TABLE question
(
    question_id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    content     VARCHAR(200) NOT NULL,
    created_at  TIMESTAMP    NOT NULL DEFAULT now(),
    updated_at  TIMESTAMP
);
```

## 3. 버전을 나눠야 하는 경우

아래 중 2개 이상이 필요하면 파일을 나눕니다.

1. `V{n}__migrate_{data}.sql`: 기존 데이터 이관 (INSERT/UPDATE)
2. `V{n+1}__add_constraint_{table}.sql`: 이관 결과를 확인한 뒤 NOT NULL / UNIQUE / FK 추가
3. `V{n+2}__drop_{table}.sql`: 기존 테이블·컬럼 삭제

- PostgreSQL은 DDL도 트랜잭션에 묶여서 실패한 파일은 통째로 롤백됩니다. 그래도 나누는 이유는 이관 결과를 확인하고 제약을 걸 수 있게 하고, 삭제를 마지막에 독립적으로 되돌릴 수 있게 하기 위함입니다.
- `ALTER TABLE`의 `ADD`/`DROP` 절에 `IF EXISTS`/`IF NOT EXISTS`를 쓰지 않음. `CREATE TABLE IF NOT EXISTS`, `DROP TABLE IF EXISTS`는 허용
- 다른 테이블 데이터에 의존하는 이관은, dev에 그 데이터가 실제로 있는지 사람에게 확인 요청 (로컬 통과만으로는 검증되지 않음)
- 기존 컬럼·테이블 삭제나 데이터 이관은 작성 전에 먼저 물어보기

## 4. 검증

1. 로컬 DB 실행: `docker compose up -d` ([docs/local-setup.md](../../../docs/local-setup.md))
2. `./gradlew test` 실행. `KiriServerApplicationTests`가 앱을 띄우면서 Flyway 적용과 `ddl-auto: validate`를 같이 검증
3. 실패 메시지별 원인
   - `Schema-validation: missing column` / `wrong column type`: 엔티티와 DDL의 이름·타입 불일치
   - `Unable to create unique key constraint ... column not found`: `@UniqueConstraint`의 `columnNames`에 필드명을 썼거나 `{"a, b"}`처럼 한 문자열로 묶음
   - `checksum mismatch`: 이미 적용한 파일을 수정함. 아직 dev에 반영 안 된 파일이면 `docker compose down -v` 후 재실행
4. DB를 띄울 수 없으면 검증하지 못했다는 사실을 보고에 남김
